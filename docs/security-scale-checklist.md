## P2 — Before someone goes viral

- [x] **P2-1 FAN_OUT chunk-cap + idempotency** `High (live correctness bug)` ✅ DONE
  - Files: `src/lib/notification-processor.ts` (FAN_OUT loop), `src/lib/qstash.ts` (payload schema), new migration `prisma/migrations/20260930120000_notification_dedupe_partial_index/`, new `test/transactions/notification-fanout.test.ts`
  - **The bug was live, not hypothetical.** `cursor` lived in a local variable, so any QStash retry (`retries: 3`) restarted the walk from follower #1; `Notification` had no uniqueness constraint, so the replay inserted silently instead of failing. Users got duplicate notifications and inflated `readAt` badge counts.
  - **Migration** adds a *partial* unique index `Notification_unread_dedupe_key` on `(recipientId, targetId, type) WHERE readAt IS NULL AND targetId IS NOT NULL`.
  - **Why partial, and why that matters:** a plain unique constraint would have silently stopped users being notified about something they had already read (a second comment on the same post, a re-follow). The existing `findFirst({ …, readAt: null })` rollup logic already reasons in terms of *unread* rows, so the predicate matches how the code thinks. The migration also folds duplicate groups' `count` into the survivor (2+3+1 → 6) so no rollup tally is lost.
  - **Validated against a real Postgres 17** (throwaway Docker container), not just asserted in a unit test: seeded a replayed fan-out (3 duplicate unread rows), an unread rollup group with counts 2+3+1, two already-*read* duplicates, and two NULL-`targetId` rows. After migrating, 10 rows → 6, counts preserved as 3 and 6, read and NULL-target rows untouched; then verified a duplicate unread insert is **rejected**, a fresh unread row for an already-read triple **succeeds**, and NULL-`targetId` inserts still work.
  - **Code:** cursor now travels *in the payload* (`notificationPayloadSchema` gained an optional FAN_OUT `cursor`), so a retry resumes instead of restarting; work is bounded at `FAN_OUT_CHUNK_SIZE 500 x MAX_FAN_OUT_CHUNKS 4` = 2000 recipients per invocation, then the tail is re-enqueued carrying its cursor; `createMany({ skipDuplicates: true })` makes any overlap a no-op.
  - **Prisma caveat:** Prisma cannot model partial indexes, so this one is invisible to `schema.prisma` and `prisma migrate dev` may propose dropping it as drift. It must not be dropped — noted in the migration file itself.
  - **Known and accepted:** two concurrent `TARGETED` deliveries can now race on the index (one succeeds, the loser gets a unique violation). The transaction is `Serializable` and QStash retries 3x, so this converges on retry — previously the same race produced a *duplicate row*, so this is strictly better. No extra retry code was added for it deliberately.
  - Tests: 12 in `test/transactions/notification-fanout.test.ts` (happy path, self-follow exclusion, `skipDuplicates` always passed, 4-chunk cap, cursor-in-payload, continuation reaches the tail without re-notifying the head, dry continuation stops, and three replay scenarios). Uses a purpose-built stub because the shared fake-prisma has no `createMany`, no `cursor` paging, and no uniqueness semantics. Full suite **1135** passing.

- [x] **BUG: followers / following list never loaded** ✅ FIXED (found while working P0-3)

- [x] **P0-2 Digest email wall — the ACTUAL fix, batching** ✅ DONE

## Decisions recorded (agreed 2026-09-30)

- Reputation is **votes-only**: no creation bonus, no self-votes. Survey-participation `+1` is the sole non-vote grant (engagement incentive).
- Deletion keeps Stack Overflow semantics: the author loses exactly the `totalVotes` that content earned. No 60-day exception for now (revisit when moderators do bulk cleanups of old content).
- Historical reputation is **grandfathered** — no backfill/recompute across the 105 models.
- Self-vote block applies to **comments and replies** as well as all 17 top-level modules.
- Pre-existing self-vote rows (if any) stay in the DB and keep counting toward `totalVotes`; their owner can no longer toggle them off. Harmless, and avoids a destructive migration.
- Cron state resolved 2026-09-30: `_vercel.json` lists exactly the four routes that exist on disk (`trim-maintenance`, `trim-soft-deleted-posts`, `daily-digest`, `weekly-digest`). `cleanup-deadlines/route.ts` and `update-trending/route.ts` are gone (trending moved to pg_cron via `update-trending.md`), and no `_vercel.json` entry points at a missing route.
- Next.js lands on **16.3.7, not the 16.3.6 first written here** — `npm audit` resolved the fix to the newest 16.3.x patch, and the vulnerable range (`9.3.4-canary.0 - 16.3.2`) means stopping one patch short buys nothing. Real exposure, not theoretical: 4 files call `ImageResponse`.
- `xlsx` was replaced by **exceljs**, not merely upgraded. SheetJS froze its npm release at 0.18.5, so the two advisories had no in-registry fix; the SheetJS CDN tarball was rejected as a supply-chain cost on every CI/Vercel build. exceljs keeps the export auditable on npm.
- P3-4 was resolved by **auditing rather than copying the CSV escape**: XLSX cells are typed strings, so the `'` prefix would have shown a stray apostrophe to researchers. A regression test now enforces the no-formula-cell invariant.
- Remaining audit findings are **documented, not suppressed**: the Prisma CLI chain (3 high, dev-only, npm's fix is a major *downgrade*) and `uuid` via exceljs (2 moderate, path unreachable in the installed version). Neither justifies the risk of forcing a major into pinned transitive tooling.
- A dependency upgrade **surfaced a latent test bug rather than causing one**: `supabase-jwt.test.ts` had been malformed since 2026-09-26 and 7 tests silently never ran. Worth remembering when a major test-runner bump fails on "clean" code.
- **Search throttles by degrading, not by throwing.** `fetchFeedPage` backs a server component *and* the client's pagination loader, so raising `RATE_LIMIT_ERROR` there would tear down the feed to report a throttle. It returns an empty page instead, and the existing empty state already reads as "nothing matched".
- **Notification dedupe is a PARTIAL index, on purpose.** The invariant is "one *unread* row per (recipient, target, type)" — which is exactly what the existing rollup code already assumes. A plain unique constraint would have quietly stopped users being notified about something they had already read.
- **Prisma cannot model partial indexes**, so `Notification_unread_dedupe_key` is invisible to `schema.prisma`. `prisma migrate dev` may propose dropping it as drift; it must not be dropped.

- **Search is deliberately NOT cached** — unfiltered pages are, but any search bypasses the cache and hits the database every time. The code comment claiming searches are "non-shareable" is only half right: that is true of the *viewer-scoped* tab, false of search text (identical rows for everyone, and viewer state is overlaid live). Search is still better left uncached, for reasons worth recording: attacker-controlled cache keys from unauthenticated surfaces, a low hit rate on diverse terms, and staleness. **P2-2 is what actually makes search affordable.**

Worth re-measuring and restoring the floor — otherwise the gate silently permits large regressions. Not reverted here because it was someone else's deliberate edit.

## When to upgrade free tiers

- Resend: digest demand > ~80/day sustained (headroom under 100).
- Supabase: indexes+tables > ~400MB or CPU throttles feed.
- Vercel: need maxDuration > 60s or daily precise timing+retries.
- Redis: `degraded:true` in logs or ~400K cmds/mo.
